## Why this task exists (read first)

The merge gate runs full `make check` for EVERY task, including this one. A red
spec on main would deadlock the whole phase at your own gate. So this task is
split by nature of each assertion:

- **A-101, A-102, A-105** are already satisfied by the skeleton. Write them as
  ACTIVE, green specs (regression guards). They must pass at your gate.
- **A-103, A-104** are NOT yet satisfiable (no `/probe`, no migrations). Write
  them as **inert drafts** under `acceptance/drafts/` (and holdout drafts under
  `<holdout>/drafts/`). Drafts use extensions that no runner picks up
  (`*.spec.ts.txt`, `*.go.txt`) so they cannot fail any gate. T-105 (later,
  also test-author) activates them by pure rename after the features land.

The drafts are the contract-first oracle: git history proves the tests existed
before the feature tasks branched. T-105 must be able to activate them with
`git mv` and NO content edits — so encode the frozen contracts below EXACTLY.

  (dev|test|prod), BASE_URL, DB_PATH, PHOTO_DIR, SESSION_KEY, IP_HASH_KEY,
  ADMIN_TOKEN, TOWN_BBOX, TZ. Valid test values are in `.env.test` (copied into

- Existing suites: `acceptance/go/healthz_test.go` (build tag `acceptance`,
  BASE_URL from env, started by `scripts/acceptance-go.sh`) and
  `acceptance/e2e/home.spec.ts` (tags `@A-000 @smoke @a11y`). Playwright
  projects: desktop-chromium, pixel-9, iphone-16 (webkit), iphone-se-320.
- Playwright config: when env `BASE_URL` is set, no webServer is started —
  specs hit that URL. Otherwise it boots `bin/server` with `DB_PATH=./test-run.db`

- Ratchet: Playwright test count must never drop (currently 12). Adding specs
  is fine. `t.Skip`/`test.skip`/`test.only`/`.fixme` are forbidden everywhere.
- You may ONLY import the Go standard library in acceptance tests. go.mod has
  no sqlite driver and you cannot add one. Any test that must touch the DB file

### acceptance/drafts/probe.spec.ts.txt — `@A-103 @smoke @a11y`

Playwright spec (must run on all projects, and against a deployed BASE_URL
with no test hooks):

1. `goto '/'` → a `<section>` with id `probe` becomes populated (HTMX loads
   `/probe` on page load; wait for it): heading role name exactly `Probe`.
2. Inside it: text `Count: N` where N is a non-negative integer, element
   `#probe-count` holds N; a button with accessible name exactly
   `Increment counter`.
3. Click the button → `#probe-count` shows N+1 (no page navigation).
4. `page.reload()` → count is still N+1 (persists in SQLite across requests).
5. `@a11y` variant: axe (tags wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa) on
   `/` with the probe section loaded → zero violations.
6. Attach the observed before/after counts as test info
   (`testInfo.attach` or console note via `test.info().annotations`) so
   deployed runs prove counter persistence across deploys.
7. No-JS variant: after `context.setJavaScriptEnabled(false)`, `goto /` shows
   the probe section (server-rendered or plain form), submitting the form
   increments the count (303 → `/`).

### acceptance/drafts/probe_go_test.go.txt — `@A-103` (Go black-box)

Spawn-based, self-contained (`BIN`, temp dirs, own port):

- `TestA103ProbeRequiresCSRF`: POST `/probe` with no token → 403; with a
  tampered token (valid shape, wrong value) → 403; counter unchanged
  (subsequent valid POST sequence yields consistent numbering).
- `TestA103ProbeIncrementsAndPersists`: GET `/` (capture cookies) → GET
  `/probe` returns 200 fragment containing `Count:` and a hidden input named
  `csrf_token`; extract token+cookie; POST `/probe` (form field `csrf_token`)
  → 200 with incremented count; SIGTERM; respawn same `DB_PATH`; GET `/probe`
  → same count. Also: POST without `HX-Request` header → 303 with
  `Location: /`.

### acceptance/drafts/migrations_go_test.go.txt — `@A-104` (Go black-box)

- `TestA104AppliesMigrations`: spawn on fresh `DB_PATH` → process stays up,
  `/healthz` 200 (migrations applied at startup without error).
- `TestA104RefusesTamperedChecksum` (driver-free byte tamper): spawn once on a
  fresh DB, wait for healthz, stop; read the DB file bytes, find the 64-char
  lowercase-hex sha256 token recorded in `schema_migrations` via regexp
  (`[0-9a-f]{64}`), replace one such occurrence with different hex of the same
  length (keep file length identical); respawn with same `DB_PATH` → process
  exits non-zero, stderr/stdout contains the migration filename
  (`0001_init.sql`) and the word `checksum`. If multiple hex tokens exist,
  tamper the first and, on unexpected pass, document in the draft header which
  token index worked — T-105 may pin the index, that is the ONLY edit allowed.
