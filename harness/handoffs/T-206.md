### Parse-order contract (the part T-205 must follow)

`r.MultipartReader()` is **single-use** on a request (verified on this
toolchain: a second call errors `http: MultipartReader called twice`), and a
streaming hand-off between handlers is impossible for the same reason. So
`Photo` owns the request's ONE multipart parse (`MultipartReader` +
`ReadForm(32<<20)`) and exposes it on `r.MultipartForm`. Two valid orders:

**Order A (Photo-first — simplest, matches the frozen comment):**

```go
func (s *Server) createLight(w http.ResponseWriter, r *http.Request) {
    LimitBody(r)                    // 1. FIRST, before any body read
    up, perr := s.Photo(r)          // 2. Photo performs the parse
    if perr != nil { status, msg := PhotoProblem(perr); http.Error(w, msg, status); return }
    // 3. read csrf_token/label/kind/lat/lon/dup_choice from
    //    r.MultipartForm.Value[...] (a later r.ParseMultipartForm is a no-op
    //    returning nil); VerifyCSRF; bbox/dup checks; store the light.
}
```

Caveat: the photo is persisted BEFORE the CSRF check in this order, so a
request that fails CSRF after a successful `Photo` leaves a stored photo
(row + file). The A-207 no-stray rule covers only 413/415 rejections, which
`Photo` refuses before writing anything — but see Order B if T-205 wants
zero-stray on CSRF failure too.

**Order B (parse-first — CSRF-safe):**

```go
LimitBody(r)
if err := r.ParseMultipartForm(photoMaxMemory); err != nil {
    status, msg := PhotoProblem(err) // *http.MaxBytesError maps to 413
    http.Error(w, msg, status); return
    // on parse error DO NOT fall through to Photo: the reader is spent and
    // Photo would answer 500 ("called twice").
}
if err := VerifyCSRF(r, r.MultipartForm.Value["csrf_token"]...); err != nil { 403; return } // nothing stored yet
up, perr := s.Photo(r) // reuses r.MultipartForm (fallback path, tested)
```

### Semantics pinned by tests (T-205 can rely on all of these)

- `Photo` returns **(nil, nil)** for: no photo field, a photo field sent as a
  plain value (no filename), a file part with 0 bytes. Photo is optional.
- Error → sentinel mapping (`errors.Is`-compatible, bare sentinels):
  body over `LimitBody` cap or `img.ErrTooLarge` → `ErrPhotoTooLarge`;
  `img.ErrPixelBomb` → `ErrPhotoTooManyPx`; `img.ErrUnsupported` →
  `ErrPhotoUnsupported`; HEIC bytes wrap the same sentinel in an unexported
  `heicUnsupported` marker (sniffed independently — img's sniff is private by
  design).
- `PhotoProblem` table: `ErrPhotoTooLarge` (and raw `*http.MaxBytesError`)
  → **413 "Photo must be at most 15 MB"**; `ErrPhotoTooManyPx` → **415
  "Photo has too many pixels"**; `ErrPhotoUnsupported` → **415 "Photo must be
  JPEG, PNG or WebP"**, with HEIC-detected input → **415 "Photo must be JPEG,
  PNG or WebP — please choose JPEG instead of HEIC"** (the draft asserts the
  "please choose JPEG" substring); anything else → **500 "internal error"**
  (wiring bugs: non-multipart request, nil `Server.Store`).
- Storage: `PHOTO_DIR/YYYY/MM/<16-hex>.jpg` (UTC), file 0644 / dirs 0755,
  dims 800×600 for the orient-6 fixture (T-202-frozen), row records path,
  dims, re-encoded byte count and sha256-of-re-encoded-bytes.
- Serving: `GET /photos/{path...}` from `s.Cfg.PhotoDir` ONLY — `Content-Type`
  exactly `image/jpeg`, `Cache-Control: public, max-age=31536000, immutable`,
  missing → 404, traversal → 404 (see nuance below), HEAD covered by the mux.

### Traversal behavior (wire nuance, both 404 in the end)

Go's mux **307-redirects** literal dot-dot paths (`/photos/../../go.mod` →
`Location: /go.mod`, which 404s — the draft-style client sees a final 404);
**percent-encoded** dot-dot (`/photos/%2e%2e%2fsecret.txt`) DOES reach
`photoServe` with `PathValue("../secret.txt")` — the resolver roots the value
(`path.Clean("/"+v)`), clamps it, and re-proves containment with
`filepath.Rel`, so it can only resolve to a guaranteed miss inside PHOTO_DIR →
404. Red-check: with both guards disabled the test suite fails with the
planted secret actually served (see table).

## Load-bearing environment facts (probe-verified, go1.27.4)

- `http.MaxBytesReader(nil, body, n)` is legal (no panic) and `errors.As`
  recovers `*http.MaxBytesError` — `LimitBody`'s frozen one-arg signature
  works.
- `multipart.Reader.ReadForm` over a capped body wraps the overflow with
  `%w` (`multipart: NextPart: http: request body too large`) — `errors.As`
  reaches it, so `Photo` maps it to `ErrPhotoTooLarge` exactly as frozen.
- `r.MultipartReader()` is NOT cached — second call errors. Basis for the
  parse-order contract above.
- Go stdlib `jpeg.Encode` emits **no APP0/JFIF segment** (SOI, DQT, SOF0,
  DHT, SOS only). T-202's handoff prose ("carries a JFIF APP0 only") is
  imprecise; its TESTS pin no-APP1/APP2, which holds and is what I pin too
  (SOI + no-APP1 + dims). Nobody should "fix" a missing APP0.
