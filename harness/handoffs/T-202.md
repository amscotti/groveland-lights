## What changed

- **`internal/img/img.go`** (new): `ErrTooLarge` / `ErrPixelBomb` /
  `ErrUnsupported`, `Options`, `Result`, `Process`. Guard order frozen by the
  contract: byte size first, then HEIC sniff (`ftyp` at bytes 4..8 +
  heic-family major/compatible brand), then `image.DecodeConfig` pixel cap
  (a bomb is never fully decoded), then full decode (JPEG/PNG stdlib, WebP
  via `golang.org/x/image/webp`, registered as blank imports). Orientation is
  applied as a lossless pixel permutation (`applyOrientation` + `sourceXY`)
  before a CatmullRom long-edge fit (`fitLongEdge`: integer half-up rounding,
  aspect preserved, never upscales, long edge exactly the cap; `MaxEdge <= 0`
  disables the cap). Re-encode is stdlib `jpeg.Encode` quality 85 — the
  output carries a JFIF APP0 only, never APP1/APP2/EXIF/XMP.
- **`internal/img/exif.go`** (new): `ReadOrientationJPEG` — hand-written
  APP1/TIFF parser (the packet's frozen decision: no EXIF library). Walks
  segments SOI→SOS, tolerating fill bytes and skipping non-Exif APP1s;
  parses IFD0 in both TIFF byte orders and accepts SHORT (spec) and LONG
  (real-world variant) in-place values of tag 0x0112. Returns 1 on absent,
  truncated or corrupt input; always within 1..8; bounds-checked in int64
  throughout (fuzz-clean).
- **`internal/img/img_test.go`**, **`internal/img/exif_test.go`** (new): the
  test suite below. Also a package-internal hook `testHookFullDecode`
  (nil in production) used to prove the pixel-bomb guard fires before any
  full decode — the packet's sanctioned option.
- **`go.mod`/`go.sum`**: adds `golang.org/x/image v0.47.0` and nothing else
  (see open issue 1 for why not v0.48.0). Verified diff: one require-block
  addition + two go.sum lines.

Nothing else touched. `testdata/photos/*` re-generated with
`go run ./testdata/photos/gen` during verification — every sha256 identical,
no diff (fixtures and generator untouched).

## API notes for T-206 (compiles against these signatures)

```go
img.Process(b []byte, o img.Options) (img.Result, error)   // pure, safe to call in handlers
img.ReadOrientationJPEG(b []byte) int                      // 1..8, 1 = upright/absent
```

- **Status mapping**: `errors.Is(err, img.ErrTooLarge)` → 413;
  `errors.Is(err, img.ErrUnsupported)` → 415; `errors.Is(err,
  img.ErrPixelBomb)` → 415 (draft says bomb is a 415, not 413).
- **HEIC wording**: the frozen API deliberately collapses HEIC and every
  other unsupported/undecodable input into `ErrUnsupported`, so for the
  frozen "please choose JPEG" body T-206 must do its own sniff (bytes 4..8
  `== "ftyp"` with a heic-family brand at 8..12) BEFORE calling Process, or
  sniff again on `ErrUnsupported`. My `isHEIC` is package-private on
  purpose — the API is frozen.
- **Options used by my tests** (`photoLimits()`), matching A-206/A-207:
  `MaxBytes: 15 << 20, MaxPixels: 40_000_000, MaxEdge: 1600`. MaxBytes is a
  literal cap (0 rejects every non-empty input — ErrTooLarge fires even for
  undecodable bytes, ordering is test-proven); MaxPixels likewise; MaxEdge
  ≤ 0 means "no resize cap".
- **Frozen exact dims**: both portrait fixtures (600×800 stored,
  Orientation 6 and 8) process to **exactly 800×600** under MaxEdge 1600 —
  asserted at package level here and frozen in the Go draft's A-206
  (`served photo ... want exactly 800x600`). Orientation 6/8 swaps dims;
  1..4 keeps them.
- **Result bytes** are a complete JPEG (quality 85): `Result.Width/Height`
  always equal the decoded output dims (test-asserted). T-206 can store
  `res.JPEG` directly and size avatars/thumbnails from the Result fields.
- **Alpha**: JPEG has no alpha; a PNG/WebP with transparency re-encodes with
  the alpha dropped (inherent to the target format, not a crop of pixels).
- **WebP**: decode-only via x/image; animated/extended WebP errors →
  `ErrUnsupported`. No WebP fixture exists in `testdata/photos` (see open
  issue 2).

## Open issues / notes

1. **x/image pinned to v0.47.0, not latest v0.48.0**: v0.48.0's go.mod
   requires `golang.org/x/sys v0.50.0`, so `go mod tidy` moves x/sys
   (v0.49.0 → v0.50.0) — a module other than x/image, outside my ownership
   per the packet ("go.mod/go.sum are yours ONLY for the x/image
   addition"). v0.47.0 is the newest release whose requirements fit the
   existing graph, so the diff is exactly one dependency. If the planner
   wants latest, bumping x/sys alongside is a deliberate, planner-owned
   decision.
2. **WebP has no test fixture**: `testdata/photos` carries no WebP file and
   x/image/webp is decode-only (no stdlib encoder), so the WebP path is
   exercised only through the shared registered-decoder path (and would
   degrade to ErrUnsupported if registration broke). The packet's test list
   does not require a WebP case; if T-206 wants HTTP-level WebP coverage it
   should commit a tiny fixture via `testdata/photos/gen`.
3. **Truncation semantics** (documented + tested, not a blocker): a prefix
   that cuts *inside* the APP1 segment reads as orientation 1; once the
   segment is complete the tag reads back even if scan data is missing.
   Segment integrity is checked before TIFF parsing (conservative).
4. **HEIC sniff precision**: brands accepted = heic, heix, hevc, hevx, heim,
   heis, hevm, hevs (major or compatible). `mif1`/`msf1` are accepted as
   major brands only. All of these land in ErrUnsupported either way, so
   HTTP behavior is unaffected; T-206's wording check sniffs independently.
5. **Scratch left behind (gitignored)**: `testdata/rendered/t202-verify/`
   holds a `go mod graph` dump from the dependency probe (`rm` is sandbox-
   blocked here). Gitignored via `testdata/rendered/*`, deletable at will.
6. **Pre-existing environment artifact**: `?? node_modules` (worktree
   symlink vs `.gitignore` pattern, documented in T-200's handoff §4).
   Never committed, unchanged.
7. **Coverage**: internal/img at 85.8% — the uncovered remainder is the
   practically-unreachable `jpeg.Encode` error wrap and the e2e-owned HTTP
   layer. `harness/policy.json`'s 70% floor pins internal/config and
