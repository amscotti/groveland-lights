### Semantics T-205 must build against (frozen reconciliation, matches `acceptance/drafts/README.md`)

- **Earth radius constant: 6371008.8 m** (IUGG mean). 1° of latitude = `R·π/180` = **111195.0802 m**; the test helper uses this exact reduction (pure-latitude haversine is exactly `R·Δφ` at any latitude).
- **Numbered duplicate is distance-independent**: any candidate whose non-empty `AssetNo` equals the new non-empty asset_no → `{Numbered: true, ExistingID, DistanceM}, true`. First match in slice order wins (the unique index + asset_no lookup are expected to feed the window; 25 m only bounds the SQL query, never the decision).
- **Unnumbered duplicate** requires BOTH sides unnumbered (`newAssetNo == ""` AND `candidate.AssetNo == ""`) AND `DistanceM ≤ UnnumberedRadiusM` (inclusive at 8.0). Nearest qualifying candidate is reported; on an exact distance tie the earlier candidate wins.
- **No cross-kind match**: numbered new fixture near unnumbered existing → no dup; unnumbered new fixture near numbered existing → no dup.
- Empty candidate slice → `(DupDecision{}, false)` always.

### Test values are hand-computed, not self-generated

Table expectations derive from independent closed forms — pure-latitude `R·Δφ` (111195.080 m/deg), pure-longitude `R·Δλ·cos φ` with `cos(42.76°) = 0.7342040` (verified via two independent identities), Groveland diagonal 689.745 m from the exact haversine terms, antipodes `πR` = 20015114.442 m — all at the packet's 0.5 m tolerance. Classify fixtures place points via `m / metresPerDegLat` along a meridian (construction error ~µm, tolerances 0.05 m at street scale).

## Notable findings / open issues

1. **Haversine precision envelope near the antipodes (documented in `TestDistanceMProperties`)**: plain Haversine loses `~√(machine-eps)·R` precision when the `sin²` terms sum to ≈1, i.e. metre-scale error for near-antipodal legs (observed 0.048 m on a pole/antipode/dateline triple). The triangle-inequality property therefore uses a 2 m slack **only** when a leg exceeds 1.9e7 m; ordinary triples keep a 1e-6 m slack and the property is asserted for every triple (nothing skipped). Irrelevant to the 8 m decision at town scale (bbox rejects far positions first). If metre-exact antipodal distances ever matter, the complementary-angle form `π/2 − asin(√(1−s))` for `s > 0.5` recovers ~20× (Sterbenz-exact `1−s`) — deliberately NOT implemented now; the packet freezes the plain Haversine form.
2. **A-205 contract wording vs frozen reconciliation**: the contract sentence "same asset_no within 25m" is satisfied by the reconciliation in `acceptance/drafts/README.md` ("same non-empty asset_no anywhere → numbered duplicate; 25 m only bounds the candidate window"), which the packet's own test ("same asset_no anywhere is numbered duplicate", distance 2 km) freezes. Implemented per the packet/drafts, not the contract shorthand.
3. **Exact-8.0 m boundary** is inclusive (`d ≤ UnnumberedRadiusM`) per the API doc ("within"), but no test constructs exactly 8.000000 m (not robustly expressible in hand-chosen degrees); 7.9 m in / 8.1 m out bracket it. T-205's HTTP-side behaviour (409 + panel) should not depend on sub-mm boundary behaviour.
4. Pre-existing untracked `node_modules` on the branch (a file, not the gitignored `node_modules/` directory pattern — worth a chore task if the gate's dirty check ever counts untracked paths). Not touched here.
5. `internal/geo` currently has no consumers — T-205 wires it into the create handler (`config.BBox.Contains` stays the bbox half; do NOT ask geo for bbox logic).
