## THE BLOCKER — precise mechanism (verified empirically)

After a clean boot with both migrations, `schema_migrations` holds two rows. SQLite stores the SECOND row's cell content at a LOWER byte offset than the FIRST row's inside the leaf page (the cell-content area grows downward), so a linear scan for `[0-9a-f]{64}` hits **0002_lights.sql's checksum first** (offset 8008 = `c2a6c06c04259e5b9eb8623271aaea0d27b06a95ea312aad940194baf4481e96`), while 0001's (`a09dd824…`, what the pins expect) sits deeper in the file.

Consequences, all reproduced:

1. `internal/store/dbfile_layout_test.go::TestChecksumIsFirstAndOnlyHexTokenInDBFile` — fails at BOTH pins: `first hex token at offset 8008 = c2a6c06c…, want the recorded checksum a09dd824…` (and the file now holds 2 hex-64 tokens, tripping the `len(locs) != 1` canary). Its own header anticipates this ("a future migration … update that migration's task consciously"); the T-101 reviewer-alt finding 6 predicted it ("it will fail on a legitimate future migration … even when A-104 would still pass" — in fact the draft's `locs[0]` pin is ALSO inverted by the cell layout, so A-104's activated test fails too). **Not in my owns; I did not touch it.**
2. `acceptance/go/migrations_test.go::TestA104RefusesTamperedChecksum` (PROTECTED draft, runs in the gate via `make test-acceptance-go`) — the tamper rewrites the first token (= 0002's checksum) and the server correctly refuses:
   `store: migration 0002_lights.sql checksum mismatch (recorded deadbeef…, file c2a6c06c…): checksum mismatch` — exit non-zero ✓, "checksum" ✓, but the frozen assertion demands `0001_init.sql` ✗. **The guard contract itself works; only the frozen token index is stale.** The draft header reserves "pinning a different hex-token index in `migTamperFirstHex`" as the ONE sanctioned edit (T-105 didn't need it; now it is needed). `TestA104AppliesMigrations` passes as-is. **Never editable by me.**
3. `cmd/server/boot_test.go::TestBootSmokeRefusesTamperedChecksum` (`-tags smoke`; NOT part of `make check`, so gate-neutral but wrong) — same mechanism, tampered `f2a6c06c…` → refusal names `0002_lights.sql`, test wants `0001_init.sql`. Owner is whoever holds `cmd/server/**` (T-208 is in review with that ownership).

No legitimate implementation can dodge this: the schema oracle requires 0002 to exist; the runner records every embedded file's sha256 as 64-char lowercase hex (frozen contract); two rows are unavoidable; the cell layout then inverts the token order. I explicitly did NOT touch the runner's checksum format/insert order to dodge the scan — that would be gaming the oracle.
