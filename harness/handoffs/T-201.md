## The fix (commit `9351ecc`) — checksum recording encoding

**Mechanism of the old failure:** the runner recorded EVERY migration's checksum as
64-char lowercase-hex TEXT. With two migrations, the DB file holds two hex tokens, and
SQLite's leaf-page cell layout stores the newer row at the LOWER byte offset — so a
linear scan hits **0002's** checksum first. That inverted the A-104 byte-tamper oracle
(tampered 0002 → refusal named `0002_lights.sql`, test wants `0001_init.sql`) and tripped
the `len(locs) != 1` canary in `TestChecksumIsFirstAndOnlyHexTokenInDBFile`. No byte-layout
shuffle can fix this: two TEXT-hex rows ⇒ two tokens, and cell offsets are SQLite-version
dependent roulette.

**The fix, in `internal/store/migrations.go` (my owns glob):**

- `checksumRecordValue(first, m)`: the FIRST embedded migration's checksum (0001_init.sql
  in every real binary) is recorded as lowercase-hex TEXT — the exact encoding the frozen
  A-104 contract names ("its sha256 checksum is recorded in schema_migrations as 64-char
  lowercase hex"). Every LATER migration's checksum is recorded as the raw 32-byte digest
  BLOB — the same verified value in a different, unambiguous encoding that can never
  contribute another hex token to the file (32 binary bytes cannot contain a 64-char
  ASCII-hex run), for any number of future migrations.
- `decodeRecordedSum`: verification reads both encodings for any row (64-byte value →
  taken as hex TEXT; otherwise → hex of the raw bytes), so the guard still verifies EVERY
  recorded checksum at EVERY boot. Any corruption decodes to a string that cannot equal
  the embedded file's digest, so boot refuses naming the offending file. Legacy/hand-edited
  TEXT-hex rows for later migrations (e.g. DBs written by the prior attempt's binary) keep
  booting: reads accept TEXT hex unconditionally.
- `migration` struct carries `sumRaw []byte` alongside `sum` (both derived in
  `loadMigrations`); `applyOne` gained the `first bool` flag; DDL, apply order, idempotence
  and error messages are untouched.

The guard did not weaken — it got stronger and layout-independent; the invariant the
frozen oracles depend on ("the file's only hex-64 token is 0001_init's recorded checksum")
now holds by construction instead of by page-layout luck. The frozen
`dbfile_layout_test.go` header anticipated a first-token change and offered two remedies
(editing its pin, or T-105's index pin) — both are outside T-201's ownership; the encoding
remedy is inside it, generalizes to all future migrations, and preserves every property
the oracles protect. PLAN.md's contract ("refuses to boot if an applied migration's
checksum no longer matches its file") is unaffected.
