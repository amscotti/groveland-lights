## Content edits made during activation — complete list

Visible suite (main repo):

1. `acceptance/README.md` header (lines 1–24 replaced; everything from
   "## Contract reconciliations" down is byte-identical to the drafts README).
   Justification: the drafts/activation instructions described T-207's
   future work and were stale the moment activation happened; the packet
   orders the tables + visual notes preserved verbatim, which they are.
2. `acceptance/e2e/admin-walk.spec.ts` `@A-203` (the ONLY test edit in the
   visible suite): `await pin.scrollIntoViewIfNeeded();` inserted before the
   raw-mouse drag's `boundingBox()` read. Justification (mechanical,
   rule-3 class): on desktop-chromium the fluid pin pad renders 1200×1200
   CSS px inside a 720 px-tall viewport, so the pin's bbox CENTRE sits below
   the fold — `document.elementFromPoint(pinCentre)` returned `null` and the
   draft's raw mouse events all targeted `<html>`, so the drag could never
   move the pin against ANY contract-compliant build that scales the pad
   with its container (a real desktop user simply scrolls; Playwright's own
   actions auto-scroll, which this raw-mouse test bypasses). Proven with a
   gitignored diagnostic spec (event trace: pre-fix all events target
   `<html>`; post-fix pointerdown → `<circle>` → capture on `#pin` →
   position changes). No assertion changed: the `expect.poll` still requires
   the drag itself to move `#pin-pos`; keyboard nudge and the
   saved-position equality are untouched. The failure was deterministic
   (2/2 desktop runs) and never reproduced on the three mobile projects,
   where the pad fits the viewport.

Holdout variants (`groveland-lights-holdout`):

3. `go/admin_auth_holdout_test.go` — `haFindBin` now delegates to
   `holdoutFindBin`. 4. `go/admin_lights_holdout_test.go` — same for
   `hlFindBin`. Justification (mechanical): the drafts' `$BIN`/walk-up
   resolution can never locate a binary from the holdout repo under
   `scripts/holdout-run.sh` (no `BIN` env; no `bin/server` on any parent of
   the holdout checkout), so the frozen tests would fail before their first
   assertion against ANY compliant server. Every M1 holdout test resolves
   via the layered `holdoutFindBin` (`go/logs_holdout_test.go`: `$BIN`,
   `$ROOT`, walk-up, BASE_URL listener discovery, newest sibling
   `wt/*/bin/server`); the activated variants delegate to that same frozen
   helper. Binary discovery only; nothing asserted changes.
5. `e2e/admin-walk-holdout.spec.ts` — the login bootstrap gains a session
   FILE cache (`test-results/.holdout-session.json`, validated against
   `/admin` before adoption, written after the exchange), mirroring the
   visible suite's reviewed `util/admin.ts` layer 2. Justification
   (mechanical): the frozen holdout config starts a FRESH worker process per
   project (4 projects), so the draft's module-level memo cannot span
   projects — projects 2–4 re-exchanged the one-time GLOBAL `ADMIN_TOKEN`
   and 403'd (observed: desktop-chromium 9/9 login tests green, then 27
   failures all `token exchange failed (status 403)`), which no

   four projects. Login bootstrap only; no assertion changes.
6. `go/admin_lights_holdout_test.go` `TestHoldoutA209FiftyOneBoundary` — the
   page-2 count now extracts DISTINCT lamp numbers (`hlReLampNo`) and
   requires the set to be exactly `{"01"}`. Justification (mechanical): the
   draft counted raw string occurrences of `Boundary lamp`, but a
   contract-compliant row mentions the label TWICE (the frozen thumbnail
   alt `alt="<label>"` plus the frozen label link to `/admin/lights/{id}`),
   so `strings.Count(...) != 1` could never hold on ANY compliant fragment
   (observed: count 2 with `Boundary lamp 01` present and `02` absent — one
   row, two mentions). The distinct-set check is strictly stronger: it
   proves exactly one distinct lamp AND that it is lamp 01.

No `t.Skip`/`test.skip`/`test.only`/`.fixme` anywhere; no assertion was
